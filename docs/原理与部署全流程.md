# 静态博客「在线修改内容」的实现原理与全流程

> 本文解释：一个纯静态的 Hexo + GitHub Pages 博客，是怎么做到「在网页上改文章分类、调文章顺序」的；
> 业界通常有哪几种做法、各自代价是什么；以及本次新增功能的完整实现与部署步骤。
>
> 对象站点：<https://entropyqwe.github.io>（Hexo 8.1.2 + 主题 firefly + Cloudflare Pages Functions）

---

## 一、先把问题说清楚：静态博客为什么不能"直接改文件"

你的站点是这样的结构：

```
        浏览器                     GitHub                      GitHub Pages
   ┌──────────────┐        ┌────────────────────┐        ┌──────────────────┐
   │  访客/你     │  HTTP  │  Entropyqwe.github.io │        │  只有静态文件     │
   │  打开网页    │ ─────▶ │  （构建产物 HTML/CSS） │ ─────▶ │  没有任何后端     │
   └──────────────┘        └────────────────────┘        └──────────────────┘
```

关键事实：**访问者拿到的只是 HTML 文件，服务器不会执行你的代码，也没有数据库。**
所以"点一个按钮就把文章换个文件夹"这件事，**不可能在站点自己内部完成** —— 必须有第三方帮你写仓库。

这就是所有方案的共同切入点：**找一个能代表你写入 Git 仓库的地方**。区别只在于"这个地方放在哪、凭什么是你、密钥怎么保管"。

## 二、业界常见的五种做法

| 方案 | 原理 | 优点 | 缺点 | 适合谁 |
|---|---|---|---|---|
| **A. 本地编辑 + git push** | 电脑上跑 `hexo new` / 手改 md，然后 push | 零额外设施、最安全 | 必须有电脑、会用命令行；手机上完全没法改 | 只在自己电脑上写作的人 |
| **B. Git-based CMS**<br>（Decap CMS / Sveltia CMS） | 在站点里放一个 `/admin` 页面，登录后它调用 Git 平台的 API 提交文件；登录走 OAuth | 现成 UI、支持草稿/预览/媒体库、社区成熟 | 需要配 OAuth 回调（GitHub OAuth App 或 Netlify 托管）；UI 是通用的，不一定贴合你的主题 | 想开箱即用、不想自己写后端 |
| **C. Serverless 函数 + Git API**<br>**← 你现在这套** | 浏览器 POST 给你的云函数；云函数校验口令后，用存在**服务端**的 PAT 调 GitHub API 写文件 | 完全可控、UI 可完全贴合自己主题、口令与 PAT 都不进前端、免费额度足够 | 要自己写函数与面板；需要管理 Cloudflare 账号 | 想做成自己专属后台的人 |
| **D. Headless CMS**<br>（Strapi / Contentful / Sanity） | 内容存在 CMS 的数据库里，构建时再拉取生成静态站 | 编辑体验最好、有多人协作/审核流 | 内容**离开 Git**，站点构建依赖外部服务；自建要养服务器 | 团队协作、内容量大 |
| **E. 把 PAT/口令写在前端**<br>（❌ 错误示范） | 网页 JS 里直接放 token 调 GitHub API | "能跑" | **token 对所有人可见**，任何人可读取并删光你的仓库 | 任何人都**不**适合 |

### 一句话结论

- 只想偶尔写文章 → **A** 就够；
- 想要现成后台 → **B**（Decap/Sveltia）；
- 想要"完全按自己想法定制、又不想托管后端" → **C**（你选的路，也是本文重点）；
- 团队多人 → **D**；
- **E 永远不要**。

## 三、你现有架构的完整拆解

你已经用方案 C 做了两个功能（在线发布文章/动态、相册上传删除）。它的分层是：

```
① 浏览器（主题里的 EJS 弹窗）
     │  用户在输入框填「口令」，点按钮
     │  POST https://<项目>.pages.dev/publish
     │  body: { key: "你输入的口令", title, text, images:[...] }
     ▼
② Cloudflare Pages Function（跑在 Cloudflare 边缘的 JS 函数）
     │  if (key !== env.UPLOAD_KEY) return 403     ← 口令校验在这里，服务端
     │  用 env.GITHUB_TOKEN（一个 PAT）调 GitHub REST API
     ▼
③ GitHub API  →  提交到源码仓库 Entropyqwe/hexo-firefly-site
     │  PUT /repos/<owner>/<repo>/contents/source/_posts/xxx.md
     ▼
④ GitHub Actions（你的构建流水线）
     │  hexo generate  →  生成 public/
     ▼
⑤ hexo-deployer-git 把 public/ 推到 Entropyqwe.github.io 仓库
     │
     ▼
⑥ GitHub Pages 上线（1~3 分钟）
```

### 这套设计好在哪（值得记住的三点）

1. **口令是"服务端校验"，不是前端比对。**
   前端只是把口令**发过去**；真正的判断发生在云函数里，用的是 Cloudflare Secret。前端代码里搜不到口令。
2. **PAT 从不进浏览器。**
   `GITHUB_TOKEN` 只存在于 Cloudflare 的环境变量里。哪怕有人把网页 JS 全读完，也拿不到你的仓库写入权限。
3. **Git 就是你的内容数据库。**
   每次网页操作都是一次 commit —— 有历史、可回滚、可 diff，这是 Headless CMS 给不了的。

> 对比一下错误示范 E：如果把 PAT 放进前端 JS，任何访客按 F12 就能拿到一个能清空你仓库的密钥。
> 这就是为什么所有"在线改内容"的方案，都必须有一个**服务端**。

## 四、本次新增功能的实现原理

需求有两件事，先要搞清楚它们在 Hexo 里分别对应什么。

### 4.1 「文件夹」到底改什么

Hexo 里有两个长得很像"文件夹"的东西，含义完全不同：

| | 物理目录 | 分类 `categories` |
|---|---|---|
| 写法 | `source/_posts/技术/xxx.md` | front-matter 里 `categories: [技术]` |
| 影响 URL？ | **不影响**（默认 permalink 不含路径） | 影响 `/categories/技术/` 页面 |
| 影响界面？ | **完全不可见** | 侧边栏「分类」、文章上的分类标签都变 |
| 层级 | 靠目录嵌套 | `categories: [技术, 前端]` 即 `/技术/前端/` |

**你的站点用的是 `categories`**（`source/_posts` 是平的，6 篇文章全在根下）。
所以「把文章移到别的文件夹」= **改它的 `categories` 字段**。面板里输入 `技术/前端` 就会写成
`categories: [技术, 前端]`，对应网站上的两级分类。

> 顺带说明：面板还提供"物理目录"能力不是必需的 —— 对你的站点毫无可见效果，所以我没做，
> 只做真正影响展示的 `categories`。

### 4.2 「顺序」到底改什么（这里是本次最关键的技术点）

我先把主题源码翻了一遍，确认顺序由谁决定：

| 位置 | 代码 | 结论 |
|---|---|---|
| `_config.yml` | `index_generator: order_by: -date` | 首页按 **date 倒序** |
| `themes/firefly/layout/archive.ejs:20` | `site.posts.sort('date', -1)` | 归档按 **date 倒序** |
| `themes/firefly/layout/index.ejs` | 直接遍历 `page.posts`，**不重排** | 主题不插手顺序 |
| `themes/firefly/layout/_partials/post/post-card.ejs:9` | `isPinned = post.pinned \|\| post.sticky > 0` | 只用于 `data-pinned` **角标**，不参与排序 |

**所以：`date` 是唯一决定顺序的原生机制。** 你原本的想法完全正确。

⚠️ 同时发现一个问题：你文章里写的 **`top: true` 是个死字段** —— 主题读的是 `pinned` / `sticky`，
`top` 从来没被使用过（`开站啦.md` 以为自己在置顶，其实没有）。本次面板没有采用它。

### 4.3 陷阱：日期进了 URL

你的 `_config.yml` 是：

```yaml
permalink: :year/:month/:day/:title/
```

也就是说 `kirin9020-scan.md` 现在的地址是：

```
/2026/09/06/kirin9020-scan/
        ↑ 来自 date 字段
```

**如果直接改日期，这个 URL 就变成 `/2025/09/01/kirin9020-scan/` —— 旧链接全部 404。**
（外链、书签、搜索引擎收录全废。）

#### 解法：用 front-matter 的 `permalink` 把旧地址钉死

Hexo 允许文章自己在 front-matter 里写 `permalink`，它会**覆盖** `_config.yml` 的规则。
所以改日期时，我先算出这篇文章**原来的** URL，写进 `permalink`，再改 `date`：

```yaml
---
title: 麒麟9020扫描图
date: 2025-09-01 10:00:00                      # ← 改成新日期，用来调顺序
categories: [硬件]
tags: [麒麟, 芯片, 海思]
description: 麒麟 9020 芯片扫描图
cover: /images/2026/kirin9020-scan.jpg
top: false
permalink: /2026/09/06/kirin9020-scan/          # ← 旧地址钉死，永久有效
---
```

效果：**顺序变了，链接一个都没坏。**

两个细节保证它足够稳：

- **幂等**：已经有 `permalink` 的文章，再次改日期时**不会覆盖**它，所以反复调整顺序也不会漂移。
- **不凭空造日期**：拖拽重排时，是把**现有的日期集合**按新顺序重新分配（不是凭空生成新时间），
  所以你看到的日期仍然"像真的"。若两篇撞到同一秒，会退 1 秒保证严格降序。

## 五、完整部署步骤（从零复现）

### 前置条件

- 一个 Hexo 站点（源码仓库，如 `Entropyqwe/hexo-firefly-site`）
- 一个 Cloudflare 账号 + 已安装 `wrangler`
- 一个 GitHub PAT（细粒度：仅目标仓库 **Contents: Read and write**）

### 步骤 1 · 拿到插件

```bash
git clone https://github.com/<you>/hexo-post-manager.git
cd hexo-post-manager
```

### 步骤 2 · 安装到 Hexo 工程

```bash
./install.sh ~/path/to/hexo-firefly-site themes/firefly
```

它做三件事：
1. 把 `post-manager.ejs` 放进主题 `layout/_partials/`
2. 把 `manage.js` 放进工程的 `cloudflare-pages/functions/`
3. 自动把 `<%- partial('_partials/post-manager') %>` 挂到 `layout.ejs` 的 `</body>` 前

### 步骤 3 · 主题配置开开关

编辑 `themes/firefly/_config.yml`：

```yaml
manage:
  enabled: true
  # endpoint 省略则复用已有的 upload.endpoint
  # endpoint: "https://<你的项目>.pages.dev"
```

### 步骤 4 · 配置并部署云函数

```bash
cp .env.example .env
vi .env       # 填 CLOUDFLARE_API_TOKEN / CF_PROJECT / REPO / BRANCH / ADMIN_KEY
./deploy.sh
```

`deploy.sh` 会：

1. 复用/创建 Pages 项目（**必须和发布插件同一个项目**，这样 `/manage` 和 `/publish` 在同一域名）
2. `wrangler pages deploy cloudflare-pages` 上传函数
3. 把 `ADMIN_KEY`、`REPO`、`BRANCH` 写成 Cloudflare Secret
4. （`GITHUB_TOKEN` 若留空则跳过，沿用项目里已有的）

### 步骤 5 · 验证

```bash
curl -X POST https://<你的项目>.pages.dev/manage \
  -H 'content-type: application/json' \
  -d '{"key":"你的ADMIN_KEY","action":"verify"}'
# 期望: {"ok":true,"note":"身份验证通过"}
```

### 步骤 6 · 使用

1. 提交并推送源码仓库 → 等 Actions 构建完成（1~3 分钟）
2. 打开站点，右下角多出一个 **⚙️** 按钮
3. 点开 → 输入管理密钥 → **身份验证**
4. **📁 分类 / 文件夹** 页：
   - 「新建分类」填 `技术` 或 `技术/前端`（斜杠 = 子文件夹）
   - 「现有分类」可重命名 / 删除（重命名会连带其后代分类）
   - 「文章归属」每篇一个下拉框，选完即保存 → 完成"换文件夹"
5. **🔀 文章顺序** 页：
   - 拖动行，或点 ▲▼ 调整
   - 点「改日期」可精确指定某篇的发布时间
   - 点「保存顺序」→ 自动重写 date + 写好 permalink

## 六、安全须知

| 事项 | 说明 |
|---|---|
| 管理密钥 | 只存 Cloudflare Secret（`ADMIN_KEY`），**不要**写进前端、README、Git |
| PAT 权限 | 只给目标仓库的 **Contents: Read and write**，别给 `repo` 全权限；定期轮换 |
| 口令强度 | 是唯一的门槛，务必用足够长的随机串；泄露即等于交出仓库写权限 |
| 传输 | 口令在请求体里明文，依赖 HTTPS 保护；Cloudflare 默认 HTTPS，不要降级 |
| 建议 | 可再加一层 Cloudflare Access（邮箱验证）挡在 `/manage` 前面，防护力大幅提升 |

> ⚠️ **本次对话里出现过你的 SSH 私钥口令和管理密钥明文，请务必轮换：**
> - 换 SSH 口令：`ssh-keygen -p -f ~/.ssh/id_ed25519`
> - 换管理密钥：改 `.env` 里的 `ADMIN_KEY` 后重跑 `./deploy.sh`

## 七、排错

| 现象 | 排查 |
|---|---|
| 右下角没有 ⚙️ | 主题配置里 `manage.enabled` 是否为 true；`endpoint` 是否取到；`hexo clean && hexo g` |
| 点「验证并进入」报 403 | 密钥与 Cloudflare Secret `ADMIN_KEY` 不一致 |
| 报 500 未配置 GITHUB_TOKEN | Pages 项目缺 `GITHUB_TOKEN`（先跑一次发布插件的 `deploy.sh`） |
| 报 500 未配置 ADMIN_KEY | `deploy.sh` 没跑完，或 secret 名写错 |
| 改了但网站没变 | 正常，要等 Actions 构建（1~3 分钟）；去仓库看 commit 是否产生 |
| 改了日期后旧链接 404 | 检查该文 front-matter 是否已写入 `permalink`（本插件会自动加） |
| 分区没出现在侧边栏 | 该分类下没有文章（Hexo 分类由文章决定），把文章移进去即可 |

## 八、一句话总结

静态博客做"在线改内容"，本质是 **把写仓库的权限从浏览器挪到服务端**：

```
浏览器只负责收集你的意图和口令  →  服务端校验身份 + 持有 PAT  →  写 Git  →  CI 构建  →  Pages 上线
```

而"改文件夹"和"调顺序"落到 Hexo 里，就是改 front-matter 的两个字段：
**`categories`（文件夹）** 和 **`date`（顺序，用 `permalink` 保住旧链接）**。
